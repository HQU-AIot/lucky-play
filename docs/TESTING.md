## 一、后端自动化测试（21 项全绿）

`uv run --no-config pytest -q` → **21 passed**：

- 概率数学（test_lottery.py，10 项）：per_win 线性转移、总概率质量守恒、补货回流、depleted 整移、零库存边界、off 模式、零权重抽取、概率表归一。
- 接口集成（test_api.py，11 项）：公开奖品接口（字段/不泄露权重）、抽奖形状与库存扣减、后台 401 鉴权、权重修改与概率联动、动态模式校验 422、库存更新、负权重拒绝、历史与清空、**并发不超卖**（16 线程抢 1 件大奖，恰好发出 1 件且抽空后必为谢谢参与）、全部补货。

测试过程中修复的问题：
1. `executescript` 隐式提交导致建库事务 ROLLBACK 落空 → 改为逐条 execute + `in_transaction` 守卫。
2. per_win 模式奖品抽空瞬间最后一份概率未转移 → 无法再被抽中的奖品在两种动态模式下都整体让出权重（数学上连续）。

## 五、概率全链路蒙特卡洛核查（2026-09-26）

针对"概率是否对得上"做统计实证验证。新增独立核查脚本 `scripts/prob_check.py`：
理论概率由脚本按 DESIGN.md §4 语义**独立推导**（不调用实现代码），抽样走真实代码路径
（`pick_result` → `Store.draw` → HTTP API），两侧不一致会以 z 分数暴露。判定标准：
单格 |z| < 4（全脚本约 70 个检验格合并误报率 <0.5%）。

| 组 | 内容 | 样本量 | 结果 |
| --- | --- | --- | --- |
| 1 冻结态分布 | 7 种状态 × 模式（全新/中盘残局/全空/谢谢权重 0/奖品权重全 0 × per_win/depleted/off）直接抽 `pick_result` | 7 × 20 万 | 全部通过，最大 \|z\| = 1.75 |
| 2 概率守恒 | 300 个随机状态 × 4 种开关组合：per_win/depleted 总质量恒等 ΣW+W0；off 恒等可用质量+W0；概率表恒和 1 | 1200 组 | 零异常 |
| 3 Store 全链路 | 默认种子库存抽到全空（非平稳，逐抽累积理论期望）+ 200 万库存近似平稳；含不超卖/扣减=中奖/流水对账 | 844 + 40,000 抽 | 通过，最大 \|z\| = 2.05 |
| 4 HTTP API | `/api/sample` 无副作用实证（库存/流水零变化）+ 采样分布 3 万 + `/api/draw` 分布 4000（每千抽刷新理论期望） | 34,000 | 通过，最大 \|z\| = 1.94 |

线上服务（127.0.0.1:8666，当时配置：谢谢权重 22.5、余量 91/126、per_win）只读实测
4000 个 `/api/sample` 样本：最大 |z| = 0.94，与实时理论分布一致。

开发过程中的一个插曲（记录以为鉴）：第 4 组首轮报"全体偏离 ~10 倍"，逐批调试后确认
抽奖系统无任何问题，是脚本自身的统计口径 bug——期望只累加"被抽中 key"的概率，等价于
用观测×概率当期望（循环推导）。已改为每抽累加整张概率表后全绿。该插曲同时反证：
脚本的独立理论推导与实现走向不一致时确实能被 z 检验抓住。

运行方式：`uv run python scripts/prob_check.py`（快速回归加 `fast` 参数，样本减半）。
脚本使用独立临时数据库（退出自动清理），绝不触碰 `data/` 下的真实库；调完权重/库存后
可随时重跑复核。表中 |z| 为记录当日单次运行值——API 层抽样用 `SystemRandom`，逐次运行
数字会浮动，复核时以"全部 |z|<4"为判据，不必精确复现数字。
